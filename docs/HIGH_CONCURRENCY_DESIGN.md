# 邮件系统高并发改造技术方案

- 文档日期：2026-11-17
- 状态：2026-11-19 最终交付构建完成本地复测，单实例、双实例、搜索和附件共 12 个正式轮次通过。测试范围与容量边界见 HIGH_CONCURRENCY_REPORT.md。
- 目标环境：本地 Docker Compose
- 目标：在本地实现并验证高并发关键机制，用可复现的性能数据和故障实验支撑简历

## 1. 目标与边界

保留 Java、Spring Boot、MyBatis、MySQL 和 Vue 技术栈，重点完成查询优化、可靠异步投递、Redis 用户级限流和双后端验证。采用模块化单体，不引入微服务、分库分表或 Kubernetes。

本期暂缓对象存储、完整监控平台和线上高可用建设。附件继续使用本地存储，两个后端容器挂载同一个 Docker 卷。该架构用于验证单机多实例，不代表跨主机或生产高可用。邮件范围仍是注册用户之间的站内邮件，不新增 SMTP/IMAP 网关。

## 2. 当前问题与改造方向

以下为前期代码检查得到的基线判断，实施前须针对 D 盘工作副本复核。

| 模块 | 当前问题 | 实现内容 | 验证证据 |
| --- | --- | --- | --- |
| 查询 | 列表全量读取、逐封补查收件人 | 分页、批量查询、消除 N+1、联合索引优化 | SQL 数量、执行计划、优化前后延迟与吞吐 |
| 发信 | 请求内完成识别、逐人写入和通知，事务较长 | RabbitMQ 异步投递、有界消费并发 | 提交延迟、实际投递延迟、积压与恢复时间 |
| 可靠性 | 缺少持久化异步任务与重复处理保护 | Outbox、请求与消费幂等、重试、死信及人工重放 | 故障恢复记录、受理任务核对、重复投递检查 |
| 限流 | 缺少跨实例共享用户额度 | Redis Lua 原子令牌桶 | 双实例请求消耗同一份额度 |
| 扩展 | SSE 连接只在单进程中，附件依赖本地目录 | 双后端、Redis 广播、共享附件卷 | 跨实例通知、实例退出与附件访问验证 |

## 3. 技术架构

| 组件 | 职责 |
| --- | --- |
| Nginx | 前端静态资源与双后端请求分发 |
| Spring Boot + MyBatis | API、投递消费者、任务发布器，保持同一代码库 |
| MySQL | 邮件、收件人快照、投递状态、Outbox 和幂等记录的事实来源 |
| RabbitMQ + Spring AMQP | 投递任务削峰、确认、重试与死信 |
| Redis | 用户级限流和跨实例通知广播 |
| Docker 共享卷 | 单机双实例附件访问及模型快照共享 |
| 基础指标、结构化日志、k6 | 容量测试、性能对照和故障验证 |

```text
浏览器 → Nginx → 后端 A / 后端 B → MySQL
                        ├→ Redis：限流、通知广播
                        ├→ 共享卷：附件、模型快照
                        └→ Outbox 发布器 → RabbitMQ → 投递/学习消费者
```

保留单实例启动配置，用于性能对照。暂不叠加框架大版本升级。

## 4. 查询与数据库优化

1. 所有邮件列表及搜索分页，默认每页 20 条、最多 100 条。按时间和邮件 ID 稳定排序，使用游标翻页。
2. 当前页收件人批量查询，列表不返回完整正文；批量解析发信收件人，批量插入收件人记录。
3. 根据实际 SQL 和执行计划选择联合索引，记录扫描行数与耗时，避免仅凭字段名称堆叠索引。
4. 优先级整理保存计算后的分数并分页读取，避免每次加载全部邮件后排序；排序游标包含排序分数和稳定的唯一标识。
5. 明确请求线程、连接池和消费者并发上限；两个实例共享数据库连接预算，避免增加实例后耗尽连接。
6. 搜索第一版保留 MySQL，使用分页和负载控制，单独报告模糊搜索性能。

## 5. 可靠异步投递

### 5.1 主流程

```text
提交请求
 → 校验用户、收件人、正文、附件及幂等键
 → 同一事务保存邮件、收件人快照、PENDING 状态、Outbox 事件
 → 提交事务并返回“已提交”
 → 发布器领取 Outbox，发送 RabbitMQ 并等待发布确认
 → 消费者执行识别并写入收件箱
 → 提交投递状态
 → 确认消费，触发通知
```

默认每封最多 100 个去重后的收件人。被识别为垃圾邮件的邮件进入垃圾箱；DELIVERED 表示站内投递记录已落库，不代表用户已读。

### 5.2 状态与身份

- 状态：PENDING、PROCESSING、DELIVERED、FAILED。
- 前端展示已提交、处理中、已送达、发送失败，不把入队成功描述为投递完成。
- 消费者显式从任务读取发件人及业务上下文，不依赖请求线程的登录上下文。
- PROCESSING 必须支持处理租约超时后的恢复；重新处理前核对最终状态，避免任务因进程退出永久停留。

### 5.3 Outbox 与幂等

- 业务记录与 Outbox 在同一数据库事务中提交，禁止先提交业务后仅依赖一次内存事件发布。
- 多实例发布器通过数据库领取和租约机制竞争任务，故障后可重新领取。
- 发布确认后更新 Outbox；发布失败或确认结果不明时允许重发。
- 请求幂等按用户和 Idempotency-Key 隔离：同键同内容返回原邮件，同键不同内容返回冲突。前端重试保留原键。
- 投递依靠数据库唯一约束和条件状态更新幂等处理，不能仅使用内存标记。
- 业务事务提交后才确认消费；提交成功但确认丢失时，重复消息不能重复创建收件箱记录。

### 5.4 重试、死信与恢复

- 临时故障在初次处理失败后，按 1 秒、5 秒、30 秒延迟重试，共 3 次重试；参数集中配置。
- 耗尽后进入死信队列并标记 FAILED；提供本地管理脚本查询和人工重放，重放继续遵循幂等规则。
- 状态变更与重试、死信、通知事件之间的交接需要持久化记录，可复用 Outbox，防止进程在交接窗口退出造成任务悬空。
- RabbitMQ 使用持久化队列、持久化消息、发布确认、不可路由消息处理和手动消费确认。
- RabbitMQ 不可用时，已受理事件保留在 Outbox；积压超过可配置的待处理容量时，新提交返回明确的繁忙错误。
- 消费并发、预取数量及线程池均有上限，禁止无界创建任务。

### 5.5 模型与附件

- 默认关闭外部大模型；规则和本地固定版本模型参与识别。
- 学习任务单独排队，由单一消费者训练，发布带版本的模型快照；双实例加载同一版本，快照采用临时文件写入后原子替换。
- 附件发送前先暂存，提交时校验归属并绑定，避免先投递后上传；定期清理过期且未绑定的附件。
- 两后端挂载同一附件卷，数据库不保存依赖宿主机 C 盘绝对路径的文件位置。

## 6. Redis 限流与跨实例通知

### 6.1 用户级限流

- Redis Lua 原子实现令牌桶，以认证用户为键；默认每分钟补充 10 个令牌，容量 10，两个实例共享额度。
- 超限返回 HTTP 429 和重试提示。
- Redis 不可用时发信入口返回暂时不可用，读取接口继续工作；不自动降级为各实例独立额度。
- 吞吐测试单独使用高额度配置，限流实验使用默认配置，测试报告明确区分。

### 6.2 SSE 通知

- Nginx 分发至两个后端，统一 JWT 配置，不依赖粘性会话。
- Redis Pub/Sub 广播新邮件提示，各实例仅向本机 SSE 连接推送。
- 同账号支持多个连接；连接清理按连接标识处理，避免旧连接回调误删新连接。
- 通知仅在投递事务提交后产生；Pub/Sub 不承担可靠投递，断线重连后主动查询邮件及投递状态。
- Redis 中断期间允许提示遗漏，已落库邮件仍必须可查询。

## 7. 接口与前端变化

| 接口行为 | 调整 |
| --- | --- |
| 发信 | 增加 Idempotency-Key 请求头和附件 ID 列表；返回 HTTP 202，业务数据包含 mailId、status |
| 状态查询 | 新增仅发件人可访问的投递状态接口，提供状态及可读失败原因 |
| 邮件列表与搜索 | 返回 items、nextCursor、hasMore；前端分批加载 |
| 前端发送体验 | 展示处理中、送达、失败；使用 SSE 提示配合状态轮询刷新 |
| 本地验证辅助 | 测试配置增加实例标识响应头与可控故障注入，普通配置禁用故障注入 |

管理脚本不开放为普通用户可访问的管理 API。新增表和字段采用增量数据库迁移，历史邮件标记为已投递；前后端配套更新。

## 8. 本地性能实验

### 8.1 环境与数据

- Docker Compose 启动 Nginx、两个后端、MySQL、Redis、RabbitMQ；保留单实例配置。
- 保存硬件、Docker 资源限制、软件版本、连接池、消费并发和测试配置。
- 固定随机种子，先用 10 万封邮件调试，再以 100 万封邮件验证；包含一个拥有 10 万封邮件的账号。
- 增加结构化日志、基础指标和查询脚本，暂不部署完整监控平台。日志不记录密钥、令牌和邮件正文。

### 8.2 测试方法

1. 变更前先保存基线，优化前后使用相同硬件、数据、负载和预热流程。
2. k6 分别测试列表、详情、提交和状态查询；搜索、附件独立测试。
3. 每组正式测试 10 分钟，重复 3 次；保存每次原始结果，汇总各次指标及中位结果。
4. 逐档增加请求速率，记录成功吞吐、P50/P95/P99、错误率、CPU、内存、数据库连接和队列深度。
5. 独立测量提交接口延迟与提交到投递完成的端到端延迟；记录积压恢复时间，避免仅展示入队速度。
6. 单实例与双实例先使用相同总连接池、总消费并发预算；记录各实例资源配额和机器总资源，不预设吞吐翻倍。
7. 基准实验结束并排空任务后再比较最终投递结果，避免忽略测试结束时仍在排队的邮件。

### 8.3 初始实验目标

暂以 100 请求/秒、普通接口 P95 ≤ 500ms、非预期错误率 < 1% 为目标，实际容量由本机结果确定。这些数值不是已达成的能力或生产承诺。

限流产生的预期 429 单独统计，不计为非预期错误，但必须报告其数量。若采用混合负载，固定为 80% 列表/详情、10% 状态修改、10% 发信提交，每封 5 个收件人，并单独计入实际状态轮询请求。

## 9. 故障与一致性验收

| 实验场景 | 验收条件 |
| --- | --- |
| 同一幂等键并发提交 | 只有一封邮件；同键不同内容返回冲突 |
| 消费事务提交后、确认前终止消费者 | 重新投递后无重复收件箱记录 |
| 数据库提交后、发布前终止后端 | 重启后 Outbox 恢复发布 |
| 发布确认后、更新 Outbox 前终止发布器 | 允许重发，业务结果不重复 |
| RabbitMQ 停止再恢复 | 已受理邮件可恢复投递，无静默丢失 |
| 持续注入处理失败 | 初次处理及 3 次重试后进入死信，人工重放可恢复 |
| PROCESSING 期间终止消费者 | 租约到期后可恢复，不永久悬空 |
| 同用户请求交替进入两个实例 | 合计只消耗同一个令牌桶额度 |
| 收件人连接 A、投递由 B 完成 | 收到通知，并可查询邮件 |
| 一个后端停止 | 新请求经重试可由存活实例处理，SSE 重连后刷新邮件 |
| Redis 停止 | 新发信明确提示暂不可用，读取仍可使用 |
| 附件跨实例访问 | 上传、下载落在不同实例仍成功 |
| SSE 旧连接关闭与新连接建立交错 | 新连接不被旧连接回调删除 |

以客户端实际受理清单核对数据库：每封已受理邮件最终有可解释状态，成功投递无重复，失败有原因且可恢复。HTTP 响应丢失的请求通过原幂等键重试核对，不能直接视为未受理。

## 10. 实施顺序与完成标准

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| 1：基线与查询优化 | 保存原始数据；分页、批量操作、索引优化 | 有相同条件下的 SQL 数量、执行计划和性能对照 |
| 2：可靠异步投递 | 状态机、Outbox、RabbitMQ、幂等、重试、死信、前端与附件流程 | 主流程可运行，关键中断恢复实验通过 |
| 3：限流与双实例 | Nginx、共享卷、广播、模型版本、分布式限流 | 跨实例功能与故障验证通过 |
| 4：复测与整理 | 正式压测、数据核对、报告与架构图 | 原始结果可追溯，另一台满足条件的机器可按说明复现 |

## 11. 交付物与简历使用原则

最终交付：

- 一键启动配置、固定种子数据生成工具、压测脚本、故障验证和死信管理脚本。
- 测试报告：硬件、数据规模、软件版本、配置、原始结果、对照表及关键截图。
- 架构说明：选用消息队列的原因、幂等与恢复机制、单机部署局限。
- 数据库增量迁移和本地运行说明。

简历仅使用实际测得的数据，明确说明“本地压测”“双实例验证”。不把在线连接数写成请求吞吐，不把提交成功写成投递成功，不把单机多实例写成生产高可用。未达到目标时如实报告实测值和瓶颈。

对象存储、完整监控平台、跨主机高可用和外部邮箱接入仅列为后续演进方向，不计入本期完成能力。
